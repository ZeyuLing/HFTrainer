**Status**: Comprehensive Review of SOAR + Related Works

## Executive Summary

### Key Finding: SOAR Provides a Natural Bridge to Physics-Based Feedback

The SOAR framework offers a mathematically elegant foundation for integrating physics feedback:

| Component | SOAR Native | Physics Adaptation |
|-----------|------------|-------------------|
| **Correction Oracle** | Clean target `z0` itself (`v_corr = (z_re - z0)/σ`) | Physics simulator output (`v_phys_corrected = simulate(z_re)`) |
| **Signal Type** | Dense per-frame velocity supervision | Physics constraints (foot contact, IK feasibility, balance, …) |
| **Training Cost** | No additional labels needed | Requires differentiable simulator or reward model |
| **Existing Support** | SOAR already implemented in HY-SOAR repo | Must build simulator bridge layer |

### Three Possible Approaches (Ranked by Feasibility)

1. **Hybrid SOAR** (✅ Most Feasible): Run SOAR post-training as-is, then optionally add physics-guided re-training phase
   - Zero code changes to SOAR itself
   - Physics feedback only in second stage
   - Maintains SOAR's "no additional labels" property

2. **Physics-Augmented SOAR** (🟡 Medium Effort): Blend SOAR correction with physics constraints during re-noising
   - Modify re-noise step: `z_re = blend(z_re_base, z_re_phys)`
   - Requires differentiable simulator
   - Experimental but theoretically sound

3. **Physics Reward Model + RL** (🔴 High Complexity): Replace SOAR with reward-based RL (GRPO/DPO style)
   - Requires training a separate physics-prediction model
   - Higher computational cost
   - Less aligned with "no additional labels" philosophy

## Part 1: SOAR Deep Dive

### 1.1 Core Problem: Exposure Bias in Flow Matching

**The Gap:**
- **Training**: Model sees x_t sampled from **ground-truth forward process**: `x_t = (1-t)*noise + t*x_clean`
- **Inference**: Model actually receives x_t generated by **its own ODE**: `x_t = previous_x + dt * v_predicted`

After even one early step with error ε, subsequent frames enter **off-trajectory** regions never seen during training.

**In M2M's case (50-step ODE):**
- 50 steps = 50 opportunities for cumulative error
- Temporal coherence breaks: earlier frame errors propagate to later frames
- Motion completion: generated region anomalies cascade through VACE attention

### 1.2 SOAR's Solution: On-Policy Rollout + Dense Correction

**Algorithm:**
```
L_SOAR = L_base + λ * L_corr

L_base:
  - Standard SFT: MSE between model velocity and (x1 - x0)
  - Trains model on on-trajectory states

L_corr (NEW):
  - Single stop-gradient ODE rollout: v_rollout = model(x_t, context)
  - Compute off-trajectory state: x_hat = x_t + dt * v_rollout
  - Re-noise: sample auxiliary noise levels σ_prime, re-blend x_hat back into noise
  - For each re-noised point: supervise model to predict velocity towards x1
  - Loss: MSE(v_model(z_re), v_correction_target)
```

**Key Insight**: The model learns to "correct itself" from OOD states without needing a reward model or preference labels.

### 1.3 Why SOAR Doesn't Require Additional Data

- Correction target = `(z_re - x1) / σ_prime` is **derived from the clean target itself**
- No external oracle needed
- Applies to **existing training data unchanged**
- This is the core advantage over RL (GRPO, DPO, RLHF)

### 1.4 Adaptation to M2M (Already Documented in SOAR/CLAUDE.md)

**Direct compatibility:**
- M2M uses same **rectified flow** framework as SD3.5-Medium
- M2M's 50-step ODE has **worse exposure bias** than SD3.5 (more steps, temporal coupling)
- SOAR's correction applies equally to generated regions vs. known regions (via mask selection)

**Implementation**: ~100-150 lines in trainer:
```python
# SOAR correction for M2M (existing known-region aware)
with torch.no_grad():
    v_rollout = model(x_t, condition, text, t)  # stop-gradient
dt = -1.0 / K  # K=50
x_hat = x_t + dt * v_rollout  # off-trajectory

# Preserve known regions at the new timestep
if mask_aware:
    x_hat = where(keep_mask, x1, x_hat)  # known=clean, generated=OOD

# Re-noise and supervise correction on generated regions only
for auxiliary noise level:
    z_re = interpolate(x_hat, x0, α)
    if mask_aware:
        z_re = where(keep_mask, x1, z_re)
    
    v_target = (z_re - x1) / σ_new
    v_pred = model(z_re, condition, text, t_new)
    loss_corr += MSE(v_pred, v_target, mask=generation_mask)
```

## Part 2: Reference Works on Physics Feedback

### 2.1 HY-SOAR (In-House Flow+GRPO for T2I)

**Location**: `ref_repo/HY-SOAR/sora/flow_grpo/`

**Reward Functions Implemented**:
- `aesthetic_score` — aesthetic quality model
- `clip_score` — CLIP image-text alignment
- `hpsv2_score` — human preference model (HPSv2)
- `pickscore_score` — PickScore preference
- `imagereward_score` — ImageReward preference
- `geneval_score` — GenEval (composition + semantic)
- `ocr_score` — OCR accuracy (text rendering)
- `unifiedreward_score_sglang` — LLM-based unified scoring

**Pattern**: Each returns `(scores, metadata)` where scores ∈ [0,1] or similar range.

**Insight for Motion**:
- These are **post-hoc metrics**, not differentiable
- Used for RL training: compute score, backprop reward gradient
- Physics feedback would follow the same pattern:
  ```python
  def physics_constraint_score(motion, batch_metadata):
      # Run through differentiable physics simulator
      violation = check_constraints(motion, physics_model, simulator)
      # Return scalar reward [0, 1]
      reward = clip(1.0 - violation_magnitude / threshold, 0, 1)
      return reward, {"violation": violation, ...}
  ```

### 2.2 Related Robotics RL Frameworks

**Found in `ref_repo/`:**
- `UH-1/rsl_rl/`: PPO-based RL for legged robots
- `VideoMimic/simulation/`: MuJoCo-based motion imitation RL
- `ProtoMotions/`: Physics simulator integration (Genesis, IsaacGym, IsaacSim)
- `ASAP/`: Humanoid control with reward shaping

**Reward Structure Pattern**:
```python
# From legged_gym configs (ref_repo/ASAP/humanoidverse/config/rewards/)
reward_terms = {
    "tracking_error": {"weight": 1.0},
    "action_rate": {"weight": -0.01},
    "feet_contact": {"weight": 0.5},  # Encourage ground contact
    "torque": {"weight": -0.0002},
    "joint_acc": {"weight": -0.0001},
}
```

**Physics Constraints Available**:
1. **Foot contact**: feet should touch ground during stance
2. **Joint limits**: rotations stay within anatomical bounds
3. **CoM stability**: center-of-mass within support polygon
4. **Foot skating**: feet shouldn't slide when in contact
5. **IK feasibility**: motion should not require impossible joint configs
6. **Torque limits**: motion should be achievable by actuators

## Part 3: Three Proposed Approaches

### Approach 1: Hybrid SOAR (No Physics Loop)
**Status**: ✅ Lowest Risk, Ready Now

**Steps**:
1. Implement standard SOAR on top of M2M SFT checkpoint
2. Post-train for 5K-10K steps (as documented in SOAR/CLAUDE.md)
3. Evaluate: Does exposure bias reduction help?
4. *Optionally*: Add physics-aware post-processing downstream

**Expected benefit**: Cleaner boundaries, reduced edge artifacts (documented in SOAR paper: +11% GenEval)

**No additional code needed**: SOAR already written for SD3.5-Medium, adapt existing patterns

---

### Approach 2: Physics-Guided Re-Noising (Medium Risk)
**Status**: 🟡 Experimental, Requires Physics Bridge

**Core Idea**: During SOAR's re-noising step, blend simulator-corrected motion with standard SOAR:

```python
# SOAR correction phase (modified for physics)
z_re_base = (1-α) * x_hat + α * x0  # standard re-noise

# NEW: Physics-guided blending
with torch.no_grad():
    z_re_phys = physics_corrector(z_re_base)  # simulator correction
    # physics_corrector could be:
    # - Differentiable IK solver to enforce reachability
    # - Foot contact projection to reduce skating
    # - CoM-aware re-projection to improve balance
    
# Blend: preserve model's intent while respecting physics
z_re_blended = blend_weight * z_re_base + (1 - blend_weight) * z_re_phys

# Supervise model on blended target
v_target = (z_re_blended - x1) / σ_new
v_pred = model(z_re_blended, context, text, t_new)
loss_corr += MSE(v_pred, v_target)
```

**Implementation Requirements**:
1. Differentiable physics module (IK, FK, constraints)
2. Physics simulator wrapper (PyBullet, JAX-based simulator, or learnable)
3. Blending strategy for how much physics vs. SOAR

**Advantage**: No separate reward model, builds on SOAR's clean framework

**Challenge**: Differentiability and speed (need fast physics solver)

---

### Approach 3: Physics Reward Model + RL (High Complexity)
**Status**: 🔴 High Effort, Not Recommended as First Step

**Why Not**:
- Requires training a separate neural network to predict physics feasibility
- Moves away from "no additional labels" paradigm
- SOAR already shown superior to RL (GRPO) on comparables (less reward hacking)
- Would need human preference labels or automated metrics → more engineering

**When to Use**: If end-to-end differentiable physics unavailable, or if need to incorporate human preferences beyond physics

## Part 5: Key Technical Decisions

### 5.1 Physics Constraint Selection

**Must-Have**:
1. **Foot Contact**: No feet sliding when contact_confidence > 0.8
2. **Foot Skating**: Composite score < 0.005 m/frame
3. **IK Feasibility**: Joint angles within [-170°, 170°] (safe margin)

**Nice-to-Have**:
4. **CoM Stability**: COM within support polygon (frame-dependent, complex)
5. **Torque Feasibility**: Requires actuator model (not available yet)
6. **Acceleration Limits**: Frame-to-frame accel < 3g (reasonable human limit)

**Recommendation**: Start with 1+2+3, add others if training converges well.

### 5.2 Differentiability Strategy

**Option A: Learnable Proxy** (Fastest)
- Train a small neural network: `motion_small (T, 135) → physics_score_small (T, 1)`
- Use this as a differentiable approximation of physics constraints
- During SOAR, blend physics_score_small with base SOAR
- Pro: Fast, deterministic gradients
- Con: Extra model, need ground-truth physics labels

**Option B: Differentiable IK** (Most Principled)
- Use JAX-based FK/IK solver (e.g., `jax-md`, `dm_control`)
- During SOAR, run IK solver on x_re to find closest feasible motion
- Blend: `x_re_phys = ik_solve(x_re_base, skeleton_constraints)`
- Pro: Theoretically grounded
- Con: Slower (IK ≈ 50-100ms per frame in JAX)

**Option C: Post-Hoc Correction** (Simplest)
- Don't modify SOAR loss, keep it pure
- After SOAR training completes, run 1 epoch of physics-guided "polishing"
- Treat physics constraint violation as reward signal → fine-tune via RL
- Pro: Zero changes to SOAR, can reuse HY-SOAR reward framework
- Con: Two-stage training, doesn't capture physics during SOAR

**Recommendation**: Start with Option C (Phase 3 is really two separate trainings), then explore Option B if results justify it.

### 5.3 Blending Strategy

If pursuing physics-blended SOAR:

```python
# During re-noise step
z_re_base = (1-α) * x_hat + α * x0

# Physics correction (batch_size, T, D)
z_re_phys = ik_corrector(z_re_base)  # or physics_model(z_re_base)

# Adaptive blending: physics weight inversely proportional to model confidence
# (model confident → mostly use base, model uncertain → lean on physics)
model_logstd = model.compute_uncertainty(z_re_base, context, t_new)
physics_weight = sigmoid(-model_logstd / τ)  # τ is temperature
physics_weight = clip(physics_weight, 0.0, blend_max)

z_re = (1 - physics_weight) * z_re_base + physics_weight * z_re_phys

# Supervise
v_target = (z_re - x1) / σ_new
v_pred = model(z_re, context, text, t_new)
loss_corr += MSE(v_pred, v_target)
```

**Ablation Knobs**:
- `blend_max`: Maximum physics weight (0.0 = no physics, 1.0 = all physics)
- `τ`: Temperature for uncertainty-adaptive blending (0.1 = sharp, 1.0 = smooth)
- `physics_strength`: Scale of physics penalty (0 = ignore, 1 = hard constraint)

## Part 8: Open Questions

1. **Does SOAR alone solve boundary issues?**
   - SOAR targets exposure bias (off-trajectory states)
   - Boundary issue partially due to exposure bias, but also hard mask transition
   - Hypothesis: SOAR + existing VACE should help, test empirically

2. **Which physics constraints help most?**
   - Foot contact and IK feasibility seem most impactful
   - CoM stability harder to check without simulator
   - Recommend: foot contact > IK >> CoM for now

3. **Can physics be "soft" (reward-shaped) vs "hard" (constraint-enforced)?**
   - SOAR works with rewards (soft supervision)
   - RL + physics works with rewards
   - Hard constraints would require Lagrange multipliers or projection (more complex)
   - Recommend: soft physics rewards, let model learn trade-offs

4. **Integration with existing post-processing?**
   - Current pipeline: model output → foot lock cleanup → ground alignment
   - Physics phase should run *before* these post-hoc fixes
   - Or: physics-aware post-hoc (e.g., IK-clean footlock)
