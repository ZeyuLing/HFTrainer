    def compute_yaw_offset_np(robot_quat_xyzw, motion_quat_xyzw):
        """Compute yaw-only offset between robot and motion headings.
        
        Returns quaternion representing rotation to align motion to robot heading.
        """
        robot_yaw = _extract_yaw_quat_np(robot_quat_xyzw)
        motion_yaw = _extract_yaw_quat_np(motion_quat_xyzw)
        return _quat_mul_np(robot_yaw, _quat_conjugate_np(motion_yaw))

    def apply_heading_offset_np(offset_quat_xyzw, body_rots_xyzw):
        """Apply heading offset quaternion to all body rotations.
        
        Args:
            offset_quat_xyzw: Yaw-only offset quaternion (shape: 4)
            body_rots_xyzw: Body rotations (shape: [N_bodies, 4])
        
        Returns:
            Aligned body rotations (shape: [N_bodies, 4])
        """
        original_shape = body_rots_xyzw.shape
        flat = body_rots_xyzw.reshape(-1, 4)
        offset_broadcast = np.broadcast_to(offset_quat_xyzw, flat.shape)
        aligned = _quat_mul_np(offset_broadcast, flat)
        return aligned.reshape(original_shape)

ASYMMETRY EXPLANATION:
---------
Why does the ONNX model receive RAW robot state but ALIGNED motion references?

Answer: The model learns to predict actions by tracking motion targets.
        For the tracking to work, motion targets must be in the same frame
        as robot observations. Since robot state is in world frame, motion
        references must be aligned to robot's heading (otherwise tracking
        would fail due to heading mismatch).

During training (protomotions/envs/control/mimic.py):
        The same alignment happens internally in the environment.

At inference (test_tracker_mujoco.py):
        The same alignment happens externally before calling ONNX.

Result: Model sees consistently-framed inputs in both cases.
