2. COMPUTATION PARADIGM: FUNDAMENTALLY DIFFERENT
   ─────────────────────────────────────────────────────────────────────────
   
   KIMODO Loss Flow:
   ┌─────────────────┐
   │ x1_norm (198+)  │
   │ + mean, std     │
   └────────┬────────┘
            │
            ▼
   ┌─────────────────┐
   │  Denormalize    │
   │  (x1 * std + μ) │
   └────────┬────────┘
            │
            ▼
   ┌─────────────────┐
   │  FK Compute     │
   │  (motion135)    │
   └────────┬────────┘
            │
            ▼
   ┌──────────────────────────┐
   │ 3 World-Space Losses:    │
   │  • joint_pos (γ₃)        │
   │  • joint_vel (γ₄)        │
   │  • fk_consistency (γ₇)   │
   └──────────────────────────┘
   
   M2M Loss Flow:
   ┌──────────────────────┐
   │ pred_vel, gt_vel     │
   │ pred_x1, gt_x1       │
   │ (normalized space)   │
   └─────────┬────────────┘
             │
             ▼
   ┌──────────────────────┐
   │ 6 Representation     │
   │ Space Losses:        │
   │  • velocity (→ vel)  │
   │  • x1 (position)     │
   │  • keypoints3d (FK)  │
   │  • translation       │
   │  • smoothness        │
   │  • fk_consistency    │
   └──────────────────────┘
   
   Key Difference:
   • KIMODO: Denormalize → FK → World-space constraints
   • M2M: Work directly in normalized representation space
   • FK consistency in M2M is PASSED IN (pre-computed by trainer)
   • FK consistency in KIMODO is COMPUTED HERE


3. DATA DEPENDENCY ANALYSIS
   ─────────────────────────────────────────────────────────────────────────
   
   KIMODO Requires (External to M2M):
   ✓ mean: (D,) normalization mean — from trainer
   ✓ std: (D,) normalization std — from trainer
   ✓ bone_offsets: (22, 3) SMPL-22 geometry
   ✓ rotation_space: 'local' or 'global' (training convention)
   ✓ Full denormalization pipeline (must be exact)
   ✓ FK computation (expensive, called 2-4× per forward)
   
   M2M Requires (Already Available):
   ✓ data_mask_temporal: padding mask
   ✓ generation_mask: optional, but supported
   ✓ global_step: for scheduling (already tracked)
   ✓ Pre-computed fk_consistency_loss (external!)
   
   Computation Cost:
   • KIMODO: ~4 FK calls per forward (pred/gt joint_pos, joint_vel, consistency)
   • M2M: ~0 FK calls (expects pre-computed consistency)
   • Combined: Potential 2× FK overhead if both enabled


4. SPIKE DETECTION: DOES NOT GENERALIZE
   ─────────────────────────────────────────────────────────────────────────
   
   Current M2M Spike Detection:
   • Targets: Translation dimensions ONLY (first 3 dims)
   • Method: Rolling window (100 samples) + Gaussian stats
   • Threshold: baseline + 2σ (configurable)
   • Applied to: velocity_trans and x1_trans losses
   
   Why It Doesn't Work for KIMODO:
   ✗ Joint position loss has different scale (meters vs. normalized units)
   ✗ Joint velocity loss has different distribution
   ✗ Translation loss and joint position loss have uncorrelated outliers
   ✗ Would need separate detectors per loss term anyway
   ✗ Rolling window assumes similar distribution across all samples
   
   Verdict: Don't try to unify spike detection. Keep per-loss if needed.


5. FK COMPUTATION REDUNDANCY
   ─────────────────────────────────────────────────────────────────────────
   
   Current State:
   • M2M trainer pre-computes fk_consistency_loss (1× FK call)
   • KIMODO recomputes FK internally (2-4× FK calls)
   • If both enabled: 5× total FK calls (wasteful)
   
   Solution:
   • Cache FK result in ctx: world_pos_pred, world_pos_gt
   • M2M uses for consistency computation
   • KIMODO reuses instead of recomputing
   • Saves 50% of FK computation


6. FEASIBILITY ASSESSMENT
   ─────────────────────────────────────────────────────────────────────────
   
   Option A: Single Merged Class (NOT RECOMMENDED)
   ✗ 25-27 parameters in one class
   ✗ Two completely different computation paths
   ✗ Confusing: "Why does consistency work differently?"
   ✗ Testing nightmare (hard to isolate loss terms)
   ✗ Spike detection doesn't apply uniformly
   ✗ Would create 300+ line god class
   
   Option B: Unified Config, Separate Classes (RECOMMENDED) ✅
   ✅ Minimal changes to existing M2M code
   ✅ Each loss owns its logic (single responsibility)
   ✅ Single config entry point
   ✅ Easy to enable/disable either loss
   ✅ Testable independently
   ✅ Clean separation of concerns
   ✅ Extensible (add more losses later)
   ✅ M2M KIMODO can be disabled by default
   
   Option C: Shared Utilities (Supplementary)
   ✅ Extract LinearWarmupScheduler (used by both)
   ✅ Extract SpikeDetector (if generalizing later)
   ✅ Share common masking logic
   
   Recommended Path: B + C (Unified config + Separate classes + Utilities)

UNIFIED CONFIG SCHEMA (PROPOSED)
================================================================================

```yaml
loss_config:
  # Shared across all losses
  loss_type: "smooth_l1"  # or "l1", "mse"
  
  # M2M loss section (primary)
  m2m:
    velocity_weight: 1.0
    x1_weight: 1.0
    keypoints3d_weight: 1.0
    translation_weight: 1.0
    motion_smoothness_weight: 0.0
    fk_loss_start_step: 0
    velocity_loss_reduction: "component_mean"
    trans_dim_weight: 1.0
    trans_dims: 3
    
    spike_downweight:
      enabled: true
      factor: 0.3
      std_threshold: 2.0
      window: 100
  
  # Shared FK consistency (computed in trainer, used by both)
  fk_consistency:
    weight: 0.0
    warmup_steps: 1000
  
  # KIMODO loss section (optional, disabled by default)
  kimodo:
    enabled: false
    joint_pos_weight: 0.0        # Set to 10.0 in KIMODO paper
    joint_vel_weight: 0.0        # Set to 3.0 in KIMODO paper
    joint_pos_warmup_steps: 0
    joint_vel_warmup_steps: 0
    timestep_squared_weighting: true
    motion_dim: 198              # Guard: only apply if >= 198
```

Benefits:
• Single entry point for all loss configuration
• Clear organization (m2m / kimodo / shared sections)
• Easy to enable/disable KIMODO (set enabled: false or all weights to 0)
• Config can be validated for consistency (e.g., loss_type)

CRITICAL QUESTIONS ANSWERED
================================================================================

Q1: What params are truly duplicated?
A:  Only 3 of 25: loss_type, fk_consistency_weight, fk_consistency_warmup_steps
    That's ~12% true overlap, not 60%+.

Q2: What additional data does KIMODO need that M2M doesn't?
A:  Four items (all low-cost to pass):
    • mean, std (normalization buffers from trainer)
    • bone_offsets (SMPL-22 geometry, static)
    • rotation_space (training convention, scalar string)
    These are NOT expensive; they just must be correct.

Q3: Is it feasible to absorb KIMODO into M2MLoss?
A:  Technically feasible but NOT RECOMMENDED.
    Reasons:
    • Parameter explosion (27 total)
    • Two fundamentally different computation paths
    • Spike detection doesn't generalize
    • Would create unmaintainable code
    • Hard to test, hard to maintain, hard to extend

Q4: What would the unified config look like?
A:  See above. Nested dict with m2m/kimodo/fk_consistency sections.
    Single loss_type applies to all losses.
    Each section is self-contained.

Q5: Should they remain separate classes?
A:  YES. Strongly recommended.
    Each class should:
    • Own its initialization logic
    • Own its forward() computation
    • Own its loss term definitions
    • Be independently testable
    • Be independently disableable

POTENTIAL ISSUES & MITIGATIONS
================================================================================

Issue: loss_type mismatch (m2m=smooth_l1, kimodo=l1)
Risk: 🔴 HIGH — Loss computation inconsistent
Fix:  • Validate loss_type at instantiation time
      • Single loss_type parameter in config

Issue: Mean/std not provided to KIMODO
Risk: 🔴 HIGH — Denormalization wrong, outputs garbage
Fix:  • Assert in KIMODO.forward()
      • Provide in ctx dict always
      • Unit test with missing data

Issue: Rotation space mismatch (local vs. global)
Risk: 🔴 HIGH — Large numerical errors in FK
Fix:  • Store rotation_space in ctx dict
      • Validate consistency before forward()
      • Document in CLAUDE.md

Issue: FK computed twice if both losses enabled
Risk: 🟡 MEDIUM — Training slowdown (50% overhead)
Fix:  • Cache world_pos in ctx if both enabled
      • KIMODO checks for pre-computed world_pos first

Issue: Spike detection applied to all losses
Risk: 🟡 MEDIUM — Loss term explodes or freezes
Fix:  • Keep spike detection translation-only
      • Don't try to generalize to KIMODO joint losses
      • Document why in CLAUDE.md

Issue: motion_dim < 198 (KIMODO shouldn't run)
Risk: 🟢 LOW — Graceful degradation already implemented
Fix:  • KIMODO.forward() already checks and returns {}
      • M2M guards on appropriate conditions

Issue: Wrong position channel layout (Scheme-D)
Risk: 🔴 HIGH — KIMODO consistency loss wrong
Fix:  • KIMODO already handles correctly
      • No changes needed
      • Document layout in CLAUDE.md

VERDICT & RECOMMENDATION
================================================================================

ANALYSIS CONCLUSION: ✅ PROCEED WITH OPTION B (RECOMMENDED PATH)

Design Choice:
✅ Keep M2MLoss and KimodoStyleAuxLoss as separate classes
✅ Use unified config dict for single entry point
✅ Make KIMODO optional (weights default to 0, enabled default to false)
✅ Extract shared utilities (LinearWarmupScheduler, SpikeDetector)

Rationale:
1. Minimal disruption to existing M2M code
2. Each loss owns its logic (no entanglement)
3. Easy to enable/disable KIMODO
4. Testable independently
5. Extensible for future losses
6. Scales well (add new loss types without modifying existing)

Implementation Risk: LOW (mostly config + integration, no algorithmic changes)
Effort: ~3 days
Impact on existing M2M: ZERO (optional feature)
