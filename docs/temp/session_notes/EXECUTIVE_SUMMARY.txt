🔄 DATA FLOW
═══════════════════════════════════════════════════════════════════════════════

1. TEXT PROMPTS
   Curriculum levels (standing → walking → complex)
   Source: physflow_curriculum.py::PHYSFLOW_LEVELS

2. T2M MODEL GENERATION
   "a person stands still" → motion_135 (T, 135)
   Format: [transl(3) + 22*rot6d(132)]
   Models: Original + PhysFlow-trained

3. PHYSICS CORRECTION
   motion_135 → MuJoCo PD-tracking → motion_135_phys
   Provider: physflow_physics_oracle.py::oracle.correct()
   Engine: run_smpl_physics_sim.py

4. EXPORT & METRICS
   motion_135 + motion_135_phys → NPZ + SMPL mesh JSON + metrics
   Producer: physflow_eval_and_export.py

5. (OPTIONAL) ROBOT RETARGETING
   motion_135 → PyRoki keypoints → trajectory-level IK → .motion files
   Producer: pipeline_motion_to_robot.py

═══════════════════════════════════════════════════════════════════════════════
📐 KEY DATA FORMATS
═══════════════════════════════════════════════════════════════════════════════

motion_135 (Core Format)
  Shape: (T, 135) where T = frames
  Layout: [transl(3) + 22*rot6d(132)]
  Coordinates: Y-up (HyMotion convention)
  Meaning: Root translation + 22 joint 6D rotations (row-major)

SMPL Mesh JSON (Web Format)
  Type: {"type":"frames", "fps":30, "frames": [...]}
  Frame: {Rh, Th, poses, shapes, gender, mocap_framerate}
  Viewer: load_smpl.js + Three.js SkinnedMesh
  Size: 2-5MB per file (depends on motion length)

PyRoki Keypoints (Robot Format)
  Keys: positions (T, 18, 3), orientations (T, 18, 3, 3)
  Contact: left_foot_contacts (T, 2), right_foot_contacts (T, 2)
  Coordinates: Z-up (MuJoCo convention)

💡 KEY INSIGHTS
═══════════════════════════════════════════════════════════════════════════════

1. Main Demo Generation
   → physflow_eval_and_export.py is the primary entry point
   → Uses curriculum-based text prompts (8 levels, 40+ prompts)
   → Generates both kinematic and physics-corrected SMPL meshes
   → Exports metrics.json for dashboard comparison

2. Core Innovation: Physics Grounding
   → PhysFlow uses MuJoCo PD-tracking as the ground truth
   → oracle.correct() runs physics simulation to fix unrealistic motions
   → Training loop: generate on-policy → correct physics → fine-tune

3. Data Formats
   → Core format: motion_135 (T, 135) - compact, T2M-native
   → Export formats: NPZ (binary), JSON (web-viewable), .motion (robot)
   → Coordinate transforms: Y-up ↔ Z-up handled automatically

4. Optional Components
   → Robot retargeting (PyRoki V6) adds 60+ min per motion
   → RL-based tracking (alternative physics correction)
   → Batch web processing for visualization

5. Scalability
   → Quick mode: ~12 motions in 2-5 hours (GPU)
   → Full mode: ~40-50 motions in 8-12 hours (GPU)
   → Robot retargeting parallelizable: 8 workers process 12 motions in 2-3 hours
