EXECUTIVE SUMMARY
================================================================================

PRISM v3 was experiencing NaN loss values during bf16 mixed-precision training.
The root cause was that the FP32 softmax upcast attention processor was 
implemented but never activated due to a dtype mismatch in the detection logic.

SOLUTION: Extended the processor's supported precisions from (fp16) to 
(fp16, bf16) and made the config parameter explicit.

RESULT: The processor now correctly activates for bf16 inputs, computing 
attention softmax in fp32 to prevent numerical overflow.

================================================================================
ROOT CAUSE ANALYSIS
================================================================================

Problem Chain:
  1. PRISM config uses module_dtype="bf16" for mixed-precision training
  2. WanAttnProcessorFP32Upcast has _supported_precisions = (torch.float16,)
  3. Runtime detection checks: if hidden_states.dtype in _supported_precisions
  4. For bf16 input: False → Silent fallback to parent processor
  5. Parent WanAttnProcessor has no upcast → Softmax computed in bf16
  6. bf16 exp() overflow threshold: x > 11.09
  7. Attention scores exceed this threshold → exp() overflow → NaN propagation

Technical Detail:
  Softmax(x) = exp(x - max(x)) is numerically stable in theory, but in bf16
  precision with large attention scores:
    - exp(-2.6) → OK
    - exp(0.0) → 1.0
  The intermediate overflow corrupts all subsequent computations.

Why It Wasn't Caught Earlier:
  - Full processor implementation was present
  - Integration code was correct
  - But detection logic had a silent failure (dtype not in tuple)
  - No explicit config parameter = implicit defaults = hard to debug
