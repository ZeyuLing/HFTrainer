# Motion Visualization Protocols

Visualization in hftrainer is a library-level protocol, not a collection of
one-off frontends. The reusable contract lives under
`hftrainer.motion.visualization` and defines:

- task protocols: what the condition is, what the model generates, and how
  frames should be marked;
- panel roles: reference / generated / generated-native motion sources;
- frame semantics: condition markers, continuous condition ranges, generated
  ranges, and renderer-independent diagnostics;
- continuity diagnostics that distinguish a real motion discontinuity from a
  color or label transition in a viewer.

Web viewers and offline renderers are consumers of these protocol records.
They should not infer task meaning from directory names or hard-code KIMODO
condition rules locally.

## Library API

| API | Purpose |
|---|---|
| `hftrainer.motion.visualization.protocol.TaskVisualizationProtocol` | task-level condition/generated contract |
| `hftrainer.motion.visualization.protocol.PanelSpec` | panel role contract |
| `hftrainer.motion.visualization.protocol.infer_frame_semantics` | condition-marker / generated-range operator |
| `hftrainer.motion.visualization.protocol.continuity_stats` | representation-level jump diagnostics |
| `hftrainer.motion.visualization.protocol.build_case_record` | manifest-row builder shared by exporters |
| `hftrainer.motion.visualization.kimodo.KIMODO_TASK_PROTOCOLS` | KIMODO task registry |
| `hftrainer.motion.visualization.kimodo.KIMODO_PANEL_SPECS` | KIMODO panel-role registry |

The frontend contract is the serialized output of `build_case_record(...)`.
Adding a new KIMODO task should update the registry first; frontend changes
should only be needed when a new rendered representation is introduced.

existing viewer cannot represent the data.

## KIMODO Multi-Task Mesh Protocol

KIMODO visualization must be manifest-driven because different tasks have
different condition protocols. A KIMODO fixture uses:

```text
outputs/evaluation/kimodo_all_tasks_mesh_viewer_<date>/
  _manifest.json
  _captions.json
  gt/<case>.npz
  kimodo_smpl/<case>.npz
  kimodo_soma/<case>.npz
```

`_manifest.json` is a list of protocol rows generated through
`hftrainer.motion.visualization.protocol.build_case_record`. Each row must
include:

| Key | Meaning |
|---|---|
| `sid` | stable case id shown in the UI |
| `task` | stable task key, e.g. `fullbody_keyframe`, `root2d`, `bodypart_control` |
| `task_meta` | display label, task group, condition description, generated-output description |
| `panel_meta` | per-panel roles: `reference`, `generated`, `generated_native` |
| `frame_semantics` | condition frames/ranges and generated ranges |
| `condition_summary` / `generated_summary` | short UI strings for the current task |
| `missing_panels` | absent source panels with explicit reasons |
| `diagnostics.continuity` | adjacent-frame root/pose jump statistics for generated SMPL |

Task protocols:

| Task | Condition protocol | Viewer expectation |
|---|---|---|
| Text-to-motion | text prompt only | no discrete condition frames; all panels are generated/reference |
| Full-body keyframes | saved `keyframe_indices` | keyframe indices are marked as condition frames |
| Inbetween endpoints | first and last frames | endpoints are marked as condition frames |
| 2D root path | continuous root x/z waypoints | full sequence is marked as control-active |
| Constraint JSON | saved sparse KIMODO constraints | sparse markers from metadata; if metadata is absent, use the JSON protocol summary |
| Body-part control | upper/lower body mask | full sequence is control-active, panel role explains generated unconstrained parts |
| Multi-prompt / local edit | segment prompt/edit mask | full sequence is control-active unless per-segment metadata is stored |
| Style edit | style instruction | full sequence is control-active |
| End-effector control | hand/foot targets | store target metadata and GT reference when available; legacy generated-only samples must be labeled as such |

Condition markers are overlays on the generated sequence. They are not a
separate generated stream. A visible pose/root jump at or around a marker is a
real continuity issue in the exported motion or constraint pipeline and should
be debugged with `diagnostics.continuity`, not dismissed as a viewer artifact.

Build the current KIMODO fixture:

```bash
python3 scripts/analysis/build_kimodo_task_mesh_viewer.py \
  --out-root outputs/evaluation/kimodo_all_tasks_mesh_viewer_20260615_refactor \
  --clean
```

Run it:

```bash
PYTHONPATH=$PWD HFTRAINER_SKIP_AUTOREGISTER=1 \
python3 motion_annot_web/m2m_eval_viewer/retarget_smpl_app.py \
  --host 0.0.0.0 --port 8216 \

  --case-mode union --color-mode condition --list-captions
```

## Canonical T2M Viewer Schema

Each method writes:

```text
outputs/evaluation/t2m_viz/<method>/
  captions.json              # optional: {id: caption}
  000000.npz
  000019.npz
  ...
```

Each `.npz` must contain:

| Key | Shape | Meaning |
|---|---:|---|
| `motion_135` | `(T,135)` | SMPL-22 `motion_135 = [transl(3), 22×rot6d_row(132)]`, 30 fps |

Optional diagnostic keys are allowed (`gt_motion_135`, `fit_mpjpe_mm`,
`source_fps`, `target_fps`), but the viewer must be able to render with only
`motion_135`.

### Method Directory Names

Use short stable names:

| Model | Directory |
|---|---|
| GT | internal, not under `t2m_viz` |
| HYMotion | `hymotion` / `hymotion_smooth` / explicit debug names |
| T2M-GPT | `t2mgpt` |
| MoMask | `momask` |
| MoGenTS | `mogents` |
| MotionStreamer | `motionstreamer` |
| Go-to-Zero | `gotozero` |

Changing labels in the web UI should not change on-disk directory names.

## Building T2M Viewer Inputs

### Native SMPL / HYMotion Outputs

If a model already produces `motion_135`, save it directly:

```python
np.savez_compressed(out_dir / f"{id}.npz", motion_135=m135.astype(np.float32))
```

The `motion_135` rot6d block must be ROW-major local rotations.

### HML263 Baselines

For T2M-GPT, MoMask, MDM, MotionLCM and other native HumanML3D-263 baselines:

```bash
python3 scripts/eval/repack_hml263_to_prep.py \
  --pred_dir <pred_263_dir> \
  --out_dir outputs/evaluation/t2m_viz/<method> \
  --ids 000000,000019,000021,000022,000067,000073,000076,000085
```

This converts HML263 @20 fps to SMPL `motion_135` @30 fps using the same
retargeting library documented in `docs/motion/representations.md`.

### MS272 Indexed Outputs

For methods that saved indexed MS272 predictions (`<idx:06d>.npy`) from
`MotionStreamer272Evaluator.load_test_pairs()`, first map indices back to
HumanML3D ids and decode to `motion_135`. Use a dedicated repack script; do not
copy MS272 arrays into the viewer directly.

## Rendering and Recording

Interactive viewers are the source of truth. For paper/debug clips, record the
same viewer instead of writing a separate renderer:

```bash
node scripts/demo/record_threejs.js \
  --url http://127.0.0.1:8096 \
  --cases 000000,000019,000021 \
  --out /tmp/t2m_viewer_frames
```

Then stitch frames at the native fps (`30` for `motion_135` viewers). Do not cap
frame count for convenience; capped videos change apparent motion speed and can
hide jitter.

## Quality Checklist

Before showing a visualization:

1. Confirm `/api/joints/<id>` returns every method expected in the UI.
2. Confirm `T` is plausible after fps conversion (HML263 20 fps -> `motion_135`
   30 fps).
3. Confirm the method label maps to the intended directory, especially when
   comparing raw vs smoothed debug outputs.
4. Use the same set of ids across all methods; otherwise the viewer silently
   intersects directories and may hide missing predictions.
5. For retargeted HML263 baselines, inspect `fit_mpjpe_mm` on a few clips. Large
   IK errors usually indicate a representation or skeleton mismatch.

## Model-Zoo Requirement

A model is not considered visualization-complete until it has:

- at least 8 standard HumanML3D examples in `outputs/evaluation/t2m_viz/<method>`;
- a documented command to rebuild those NPZs;
- a model card link to the viewer or the exact viewer command;
- one quick API sanity check recorded in the work log.
